# 更新、Wiki 与设置流程调整设计

状态：用户已同意整体设计，并补充必须确保混合仓库中的候选适用于 GTNH；已纳入下列硬性约束。第一阶段代码已实现；并发提速、Wiki 浏览器验证、设置改造尚未实施。

## 用户目标与已确定规则

用户希望日常使用只需要选择实例、检查更新、执行更新，不必逐个判断版本或维护网络技术参数。

- 默认包含 Pre-release/Beta，选择当前绑定源中经 GTNH 目标筛选后最新发布的版本。
- Wiki 和发布说明解析出的兼容信息仅供参考。信息缺失不等于不兼容，解析结果不得阻止默认更新。
- 保留手动选择版本、锁定、下载源绑定、客户端/服务端独立管理和备份回滚。
- 缩短检查与更新等待，避免重复请求、双端重复下载。
- Wiki 反爬验证不应要求普通用户通过 F12 复制 cURL、手填 Cookie 和 UA。
- 设置应以自动识别、明确状态、少量基础选项为主。

## 现有证据

基线为 main 的 546e822，版本 1.5.1；审阅前工作区干净。现有 176 项离线测试通过，但有本地测试服务器 socket 未关闭警告。

- `sources.py` 的 GitHub 检查使用 releases/latest，列版本使用 releases?per_page=30，且列表按版本号排序；检查和执行不是同一目标策略。
- `updater.py` 的推荐标记优先已知兼容，自动选择优先正式版，两者不同。
- `check_updates` 逐端串行扫描和查询；`update_all` 虽然复用双端版本列表，仍逐个处理并强制联网。
- `downloader.update_with_backup` 每次无条件下载，临时目录不等于可复用的下载缓存。
- GUI 的多选安装按钮只处理第一项；批量流程有些失败和跳过仅进入日志。
- Wiki 四个通道串行尝试并等待；GUI 在缓存回退后仍合并数据、记录刷新时间并报告更新。
- Wiki 刷新随后查询全部 GitHub 源的发布时间，延长全局 busy 状态。
- 设置要求选择 mods 目录和输入代理地址；浏览器验证入口要求复制 cURL。

这些是代码和隔离复现结论，不是线上网络耗时测量。没有测试当前 Wiki 验证后的会话复用。

## 方案选择

采用现有 Python/Tkinter 工程渐进改造：先统一业务目标和后台任务，再改交互。保持旧配置、数据库与备份可用。

单纯调整文案不能解决重复下载和目标不一致；直接迁移到全新 UI 框架会扩大迁移、打包和回归范围。本次不先做框架迁移。

## 1. 统一发布目标

所有默认入口共用一个目标解析过程：绑定源 → GTNH 目标识别 → Release 与资产筛选 → 在合格发布中选择最新 → 下载后校验。

### GTNH 目标筛选是硬性约束

- 必须区分“适用于 GTNH 的游戏平台/构建”与“适配某个 GTNH 整合包小版本的描述推断”。前者约束自动安装，后者只作提示。
- 目标为本项目管理的 Minecraft 1.7.10 / GTNH 构建；仅有 1.7.10 字样不能保证整合包实际运行兼容。
- 仓库收录于 Wiki 不代表仓库全部发布都适用于 GTNH。不得仅凭仓库名、版本号更大或发布时间更新就接受其他 Minecraft 版本。
- 同时检查发布标识和单个资产；同一个 Release 同时提供多平台 jar 时，只允许符合目标的资产进入候选。
- 明确属于其他 Minecraft 版本或 Fabric/NeoForge 的资产排除。Forge 本身不是排除词，GTNH 也使用 Forge；必须结合目标版本判断。
- Minecraft 版本识别要求明确上下文或可靠的文件名分段，不能把 Mod 自身版本号 1.20.1 自动认成 Minecraft 1.20.1。
- 不要求所有文件名都有 GTNH 或 1.7.10。缺少版本标识的文件可使用经确认的源目标配置；混合或未知源证据不足时显示“需确认”，不能自动安装。
- 手动选择版本也不可绕过明确的平台冲突。高级过滤正则可以缩小候选范围，不能盖过明确的冲突证据。
- 混合仓库最新发布属于其他游戏版本时，应继续寻找最新的 GTNH 合格发布，而不是止于仓库最新发布。
- Release 分页设置明确预算，初始最多 5 页、每页 30 条；超预算仍未定位目标时显示搜索范围有限，不能称没有 GTNH 版本或已经最新。
- 若最新的合格 GTNH 发布没有安装资产，仍报告需手动处理，不把更旧版本冒充最新。
- 下载后静态检查 jar 的可用元数据，发现明确的平台冲突拒绝替换；元数据缺失不等于不兼容，也不能声称验证过实际游戏运行。

- GitHub 默认包含测试发布，按 published_at 选最新发布，不用版本号最大替代发布时间最新。
- 草稿不进入目标。缺失或无法解析的时间采用确定性后备排序，并在测试中覆盖。
- 保留现有 tag_regex、asset_regex、排除 sources/deobf 等文件规则。
- 最新发布没有匹配资产时显示“需手动处理”，不得默默换成旧发布后仍称最新。
- 版本锁定优先；禁用端不参与自动更新。两端是否执行分别记录。
- 兼容信息显示为“发布说明提示”，无信息显示“未提供兼容说明”；移除“推荐/不推荐”对默认行为的控制。
- 版本选择器默认选同一个目标，手动选择仍可安装旧版。
- 若最新发布时间对应的版本号低于已安装版本，默认不自动降级，列为“需要确认”；防止补发维护版本误降级。未知版本号也不得静默替换。

目标结果保留源标识、发布标识、发布时间、版本号、资产 URL/名称、提示与错误，GUI/CLI 不各自重复推导。

## 2. 检查、下载与应用

流程：扫描 → 并发获取目标 → 展示计划 → 下载 → 有序应用 → 完整结果。

- 一次扫描建立两端状态；相同源与筛选配置共享查询。不同筛选条件不能错误合并。
- 检查使用小型线程池，初始上限 4；同一端点的请求合并，遇限流停止扩散请求并说明原因。
- 用户主动检查发起条件请求；缓存用于快速显示和同次任务复用，界面显示检查时间。
- 执行使用已展示的目标，不再无条件请求版本列表。源设置改变则使相关计划失效；过旧计划重新检查并展示差异。
- 下载初始上限 3，同一资产只下载一次。不要直接并发调用目前会写 db/installed 的整个 update_mod。
- 下载按完整资产身份隔离，至少包括 URL 与文件名；避免不同仓库同名 jar 冲突。
- 下载完整性检查后再应用，两端复制同一份已验证文件。缓存损坏需重新下载。
- 备份、替换文件、记录状态有序执行；下载失败不动旧文件。一端失败不伪装成两端成功。
- 任务取消停止派发新工作；正在进行的安全替换完成后停止，不中断到一半。
- 数据写入由协调层完成，工作线程返回结果，避免并发读改写丢失字段。

性能验收以请求次数、同时执行数和双端下载次数为主，辅以可重复的模拟延迟；不承诺未经测量的公网加速倍数。

## 3. 更新交互

- “检查更新”结果直接显示名称、当前版本、目标版本、端别、测试版标记与状态。
- “更新选中”及“全部更新”先展示同样的计划，一次确认执行。逐个选版改为主动的“选择其他版本”。
- 多选安装使用全部选中项，明确展示安装端别。
- 状态含待检查、检查中、可更新、已最新、锁定、禁用、需手动、失败和取消。
- 结果汇总覆盖每个被请求的 Mod/端别，包括获取版本失败、跳过、用户取消；Mod 数与端别操作数分别表达。
- 常用页面允许浏览；与执行冲突的修改才禁用。不能让全局 busy 掩盖正在做什么。

## 4. Wiki 同步与验证

Wiki 目录用于发现 Mod，不作为已安装 Mod 检查更新的前置条件。

- 启动立即显示上次成功目录，标出上次在线同步时间；刷新期间仍可浏览。
- 目录同步与 GitHub 发布时间查询解耦，后者按需要后台获取。
- 分别记录本次尝试时间、上次成功时间与结果来源，缓存回退不得冒充在线成功。
- 有效页面先解析、验证后再替换缓存和合并；明显缩减暂不把缺失项当作已删除。保留自定义源和绑定。
- 普通网络错误、限流、验证页面分别展示；检测到明确挑战不再机械尝试所有通道并累计长等待。

### 浏览器验证的实现前置验证

目标体验是“打开验证窗口 → 用户完成一次验证 → 应用读取该浏览器会话中的 Wiki 正文 → 同步成功”。

先在隔离的应用专用浏览器配置中验证：

1. 可以正常打开站点并让用户手动完成验证。
2. 能在同一个浏览器会话内读取有效的 API/raw 内容。
3. 关闭重开后的持久化行为、过期提示及应用代理一致性可解释。
4. 不读取用户其他浏览器的 Cookie 数据库，不把 Cookie 写入日志或仓库。

仅把浏览器 Cookie 搬到 urllib 不能证明可用，因为验证可能绑定浏览器指纹。不能承诺“永久免验证”。

若选用浏览器组件，需要明确新增依赖、安装包体积和系统兼容性后再实施；优先验证 Windows 上的系统浏览器运行时方案。现有 cURL 导入仅作为高级兼容入口，不作为主流程。

无法自动完成同步时继续使用已保存目录，并提供导入 Wiki 原文文件的恢复入口；不能宣称此后备入口已经解决浏览器验证。

## 5. 设置体验

基础设置包含：

- 客户端/服务端实例：可选择实例根目录或 mods 目录；限定在所选目录及常见子目录内识别，多个候选明确选择，不全盘扫描。
- 网络：跟随系统、直接连接、自定义代理三个显式选项。测试使用当前未保存的选择，区分 GitHub API 与文件下载连通性。
- 更新策略：清晰说明默认包含测试版；指定版本/锁定放在单个 Mod 操作中。
- 备份：提供打开备份与恢复入口，保留数量放高级设置。

高级设置收纳 GitHub Token、缓存时长、Cookie/UA 和故障日志。敏感字段遮蔽。

设置校验应先完成再整体保存，失败不部分生效。给出具体字段错误和保存结果。旧 proxy=None 迁移为跟随系统，旧配置不丢失。

GTNH 版本可尝试从所选实例元数据识别，识别不到不阻止更新；仅供兼容提示使用。

## 交付顺序与验收

1. 统一目标规则：先覆盖混合 Minecraft 版本发布、同发布多平台资产、无版本标识、误把 Mod 版本识别为游戏版本、分页和 jar 冲突，再覆盖测试版、发布时间排序、无资产、兼容信息缺失/冲突、锁定与防降级；同步 GUI/CLI 文案。
2. 去重与任务协调：测试同源不同筛选、两端一次下载、并发上限、限流、失败与取消，以及备份恢复。
3. 更新交互：GUI 冒烟覆盖多选、计划确认、完整结果和失败后恢复操作。
4. Wiki：先验证浏览器方案，再实施会话同步；离线测试缓存状态、挑战页、无缓存、部分解析与旧数据保护。
5. 设置：目录识别、代理模式、输入校验和配置迁移测试；隔离数据下验证 GUI。

每步跑相关回归；交付前运行完整 Python 测试、编译检查和 git diff --check，并审阅敏感数据与生成物。无需游戏内烟测。

本次不发布、不推送、不重新打包，不操作真实 mods 或生产数据。浏览器验证需要用户参与时，只在真实验证边界请求操作。

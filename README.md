# GTNH Mod Manager

Windows 上的 GTNH 额外 MOD 管理工具，提供 Tkinter 图形界面和命令行界面。可分别管理客户端与服务端的 MOD，并管理客户端资源包、光影包。

目录来自 GTNH 中文 Wiki 的[可添加 MOD](https://gtnh.huijiwiki.com/wiki/可添加MOD)与[资源包与光影](https://gtnh.huijiwiki.com/wiki/资源包与光影)页面，也支持登记自定义来源。

- **MOD 管理**：扫描、安装、检查更新、选择版本、批量更新、启用/禁用、锁定与备份恢复。
- **Wiki 原网页**：「可添加 MOD」直接嵌入 Wiki 页面，保留原站分类、目录与说明；条目上的安装和管理按钮连接现有流程。
- **双端管理**：根据条目端别选择客户端、服务端或两端安装位置，分别记录安装状态。
- **资源包与光影**：扫描本地文件，从 GitHub Releases / Modrinth 下载，绑定来源与下载资产。
- **离线浏览**：保留上次成功同步的目录；在线刷新失败会明确报错。

工具管理额外内容，不提供 GTNH 整合包安装或游戏启动功能。下载筛选与静态校验不能代替游戏内兼容测试；修改文件前请关闭游戏或服务端，并谨慎处理整合包核心 MOD。

## 快速开始

### 免安装版

从 [Releases](https://github.com/peco331/gtnh-extra-mod-manager/releases) 下载 `GTNHModManager-<tag>-win64.zip`，解压到可写目录：

| 文件 | 用途 |
| --- | --- |
| `GTNHModManager.exe` | 图形界面，双击运行 |
| `gtnh-cli.exe` | 命令行交互菜单，也支持下方的非交互参数 |

运行数据默认保存在 exe 旁的 `data/`。升级时保留该目录，只替换程序文件。

### 从源码运行

要求 **Windows + Python 3.10 或更高版本**，GUI 需要 Tkinter；使用批处理脚本时需安装 Python 的 `py` / `pyw` 启动器。在仓库根目录执行：

```powershell
py -m gtnhmod gui
py -m gtnhmod cli
```

也可双击 `run_gui.bat` 或 `run_cli.bat`。核心管理功能使用 Python 标准库；内嵌 Wiki 网页需要 `websocket-client`，Wiki 快速请求可使用 `curl_cffi`：

```powershell
py -m pip install --user curl_cffi websocket-client Pillow
```

内嵌网页和人工验证还需本机安装 Edge 或 Chrome。免安装版的构建脚本会包含上述 Python 依赖。未安装浏览器或网页加载失败时，可切换「离线目录」使用原来的列表。

## 首次使用

1. **设置目录**：在 GUI「设置」页或 CLI 菜单 10 中填写客户端、服务端的 `mods` 路径。可用「自动检测」探测实例目录；只管理一端时只填写该端。
2. **填写可选设置**：GTNH 整合包版本用于显示兼容提示；GitHub Token 可缓解 API 限流。在网络区点击「保存并测试 GitHub API」即可保存 Token 与代理并检查配额；「仅测试当前输入」不会保存。目录和其他设置使用「保存设置」，备份数至少为 1。
3. **浏览 Wiki**：「可添加 MOD」默认显示 Wiki 原网页，首次加载正文后同步管理目录；也可点击「同步管理目录」或使用 CLI 菜单 1。网页刷新和目录同步分别进行；资源包与光影有独立的刷新入口。遇到人机验证时，在页内或工具打开的专用浏览器窗口中完成验证。
4. **扫描并核对**：查看「已安装 MOD」和「未受管 MOD」。未识别的 jar 可关联已有条目、注册为自定义 MOD 或忽略。
5. **安装或更新**：点击 Wiki 条目上的「安装」，或在离线目录中选择条目安装；已安装条目提供「查看已安装」。安装/更新可选择版本，批量 MOD 更新会先展示计划供统一确认。

手动放入文件后重新扫描即可。资源包与光影目录默认从客户端 `mods` 的上一级推断，也可在设置中分别指定。

## MOD 管理

「Wiki 原网页」使用独立的临时浏览器会话，不接管日常浏览器窗口。原站链接和说明保留；外部项目链接交给系统浏览器打开，下载与文件管理仍由工具处理。只能唯一匹配到本地 Wiki 目录的条目提供安装入口，未匹配条目会提示同步目录。网页不可用时，「离线目录」保留分类、搜索、多选安装与右键操作。

每个已匹配条目都显示「未安装」或「已安装」标识；已安装条目分别显示客户端与服务端版本、禁用及锁定状态。安装、管理操作或重新扫描后，网页中的本地状态随之刷新。

Wiki 同步后的发布时间补充查询在后台执行，整批最多等待 90 秒；失败或超时保留原日期，查询期间可正常退出。安装、更新和文件替换等操作仍须完成后退出。

已安装 MOD、离线目录、未受管 MOD 与自定义源列表提供 16 像素小图标。打开 Wiki 原网页后会复用已匹配条目的图片，离线时使用图标缓存；没有 Wiki 图标的已安装文件尝试读取 JAR 的 `mcmod.info` / `logoFile`，无图标时使用统一占位图。图标在后台只读加载，不改变 JAR 或列表操作。缩略图需要可选依赖 `Pillow`。

### 安装、选版与更新

安装默认按 Wiki 端别选择位置；未设置的端会提示跳过。Wiki 未标注端别的非星门规则条目默认按双端处理，自定义条目由用户选择端别。端别不确定或与目标不符时，请核对说明。

GitHub 来源默认包含 Pre-release / Beta，先筛选适用于 GTNH / Minecraft 1.7.10 的构建，再按发布时间选择最新合格发布：

- 明确标注其他 Minecraft 版本或 Fabric / NeoForge / Quilt 的构建会被排除。
- Wiki 可添加 MOD 目录、GTNewHorizons 官方仓库，以及明确含 GTNH / 1.7.10 标识的仓库可提供平台依据。
- 缺少平台依据的自定义来源需先确认；GUI「自定义源」支持「批量确认GTNH源」。确认不能覆盖明确冲突，更换来源后需要重新判断。
- 整合包小版本兼容提示供参考，不改变默认选版；自动更新不降级，无法比较版本时交由用户判断。
- 查询有范围上限；无法确认最新版本、最新合格发布缺少 jar 或查询失败时会显示原因。
- 同一发布存在无法区分的多个 jar 时，交互安装会要求选择具体文件；自动更新保留人工处理路径。查询失败后的过期缓存不能用来确认最新版本。

GUI 中先点击「检查更新」，仅查询**已安装、启用且未锁定**的 MOD，并保存本次结果。「全部更新」显示可更新数量，只执行本次检查出的可自动更新项目；「更新选中」使用其中选中的项目，不再重新查询或纳入检查后新增的 MOD。没有检查结果时不能执行全部更新。

检查结果超过 5 分钟，或相关文件、目录、锁定、下载源发生变化时，会提示手动重新检查，避免执行过期方案；不会悄悄启动新一轮查询。确认窗口停留期间也会校验这些变化。查询失败、资产歧义、无法比较版本和降级项目继续保留人工处理路径。单项失败不影响其他条目。CLI 的非交互 `--update-all` 仍作为独立任务执行检查和更新。

下载的 jar 会做格式及元数据静态检查，明确的平台冲突在替换前拒绝。旧文件先备份到 `data/backup/{端别}/{mod}/`，可通过「备份与恢复」（CLI 菜单 9）还原。

### 日常操作

- **启用/禁用**：在 `.jar` 与 `.jar.disabled` 之间重命名，两端独立，重启游戏或服务端后生效。
- **锁定**：让暂时不想更新的 MOD 跳过自动检查与更新。
- **从列表剔除**：隐藏条目，保留文件，可在设置中恢复显示。
- **删除 MOD**：文件移入备份目录并加 `.deleted` 后缀，可恢复；备份会按保留数量轮换，重要文件应另行保存。
- **绑定下载源**：Wiki 有多个链接时，可在详情或右键菜单中选择；绑定在后续刷新中保留。
- **GUI 快捷操作**：列表支持右键菜单、搜索与筛选；双击已安装 MOD 可在资源管理器中定位文件，版本选择器支持双击或回车确认。

### 自定义来源

| 来源 | 使用方式 | 更新方式 |
| --- | --- | --- |
| GitHub 仓库 | 填写 `owner/repo` 或仓库链接 | 筛选合格 Release；无 Release 时受限回退 tags |
| 本地文件夹 | 指定存放 jar 的目录 | 查找可解析版本的最新合格 jar |
| 手动维护 | 登记名称与端别 | 手动替换文件后重新扫描，无上游自动更新 |

CurseForge 来源的 MOD 需手动下载：工具会提供页面入口，下载后放入对应 `mods` 目录再扫描。

## 资源包与光影

入口为 GUI「资源包与光影」页或 CLI 菜单 11。资源包安装到 `resourcepacks/`，光影包安装到 `shaderpacks/`；下载的 `.zip` 保持压缩状态。整合包自带资源包仅作只读清单展示，在游戏内启用。

GUI 按 MOD 管理的方式分成四页，类型可筛选全部、资源包或光影包：

- **已安装**：显示本地版本、更新时间、来源和检查结果；支持检查更新、更新选中、全部更新、文件启用/禁用、锁定、卸载及备份恢复。
- **可添加**：默认嵌入 Wiki 原网页，保留分类、作者和说明；条目显示安装状态、禁用和锁定标识，并连接原有安装及详情流程。网页不可用时可切换离线目录。
- **未受管**：扫描 ZIP 和解压目录；可关联已有条目、登记自定义包或忽略文件，忽略只影响列表。
- **自定义源**：添加、绑定来源、查看详情和移除管理条目；移除条目保留已安装文件，Wiki 刷新保留自定义条目及来源绑定。

四个列表使用 Wiki 图片或包内的 `pack.png` 小图标，后台加载并保留离线缓存。文件禁用采用 `.disabled` 重命名；**安装状态表示文件已落盘，游戏内是否选用资源包或光影仍由游戏设置决定**，工具不修改游戏的选择配置。

「更新选中」「全部更新」仅使用本次检查得到的资产，5 分钟后或文件、目录、锁定和下载源发生变化时需重新检查。禁用、锁定、多个本地副本及解压目录保留手动处理路径；版本无法比较、查询失败和需手动选择分别显示。需要指定其他版本时，在详情的版本/资产列表中明确选择并确认安装。

**自动下载支持 GitHub Releases 和 Modrinth**。CurseForge、Discord、web.archive.org、GitLab 等来源提供手动下载提示与目标目录；下载完成后重新扫描。

- **修正来源**：在详情或右键菜单中「设置下载源」，填写 GitHub 仓库或 Modrinth 项目页；可「恢复wiki链接」取消绑定。
- **选择文件**：同一发布有多个候选 zip 且无法唯一判断时，使用「选择下载资产」绑定。绑定在刷新后保留，上游命名变化导致无法匹配时会要求重新选择。
- **登记自定义包**：对目录中的未识别文件使用「登记自定义包」，补充名称与来源后跟踪更新；自定义条目随 Wiki 刷新保留。
- **版本判断**：扫描主要依据文件名识别版本，已记录的同一文件也可保留上游版本。缺少版本号或 `Stable`、`weekly-…` 等不可比较标签需要人工判断；本地版本更高时不自动降级。
- **备份与替换**：旧文件备份到 `data/backup/{resourcepacks|shaderpacks}/{条目id}/`。新包通过校验并完成备份后再安全写入；文件名变化时，只处理该条目记录的旧 zip。
- **卸载与恢复**：卸载前完整备份已匹配文件或解压目录；恢复旧 ZIP 时先备份并移除当前版本，避免新旧 ZIP 同时保留。当前为解压目录时，先卸载再恢复备份。

结构校验检查资源包是否含 `pack.mcmeta` 或 `assets/`，光影包是否含 `shaders/`。光影 zip 内多包一层目录时会提示游戏可能无法读取配置，需自行调整。静态检查通过不代表游戏效果或兼容性已验证。

## 命令行与计划任务

首次使用先通过交互界面配置目录、同步条目并完成安装，再运行非交互命令：

```powershell
py -m gtnhmod cli --check
py -m gtnhmod cli --update-all
py -m gtnhmod cli --packs-check
py -m gtnhmod cli --packs-update
```

免安装版使用同样的参数，例如 `gtnh-cli.exe --check`。

| 参数 | 行为 |
| --- | --- |
| `--check` | 检查符合条件的已安装 MOD，打印结果 |
| `--update-all` | 直接更新可更新的已安装 MOD，无交互确认 |
| `--packs-check` | 检查已安装资源包与光影 |
| `--packs-update` | 直接更新已安装且可自动处理的资源包与光影，无交互确认 |

两个批量更新命令都只处理已安装条目。检查出现查询错误或更新出现失败时退出码为 `1`，其余为 `0`；需手动处理或跳过的条目会打印原因，退出码 `0` 不表示所有条目均已自动更新。计划任务应保留输出日志，更新任务安排在游戏与服务端关闭时运行。

## 数据与备份

数据目录按以下优先级确定：`GTNHMOD_DATA_DIR` 环境变量 → 工具目录下的 `data/` → 工具目录不可写时回退到 `%APPDATA%\GTNHModManager`。显式指定的目录需要可写。

| 相对数据目录的位置 | 内容 |
| --- | --- |
| `config.json` | 安装路径、GitHub Token、代理、备份数量等设置 |
| `mods_db.json` | MOD 目录、自定义来源、名称及下载源绑定 |
| `packs_db.json` | 资源包/光影条目、安装记录及下载资产绑定 |
| `installed.json` | MOD 版本、锁定状态与检查记录 |
| `cache/` | 下载与 API 缓存、Wiki 原文、专用浏览器会话 |
| `backup/` | MOD、资源包与光影的旧文件备份 |
| `logs/operations.log` | 安装、更新、恢复、启用/禁用等操作日志 |

默认每个 MOD / 包条目保留 3 份备份，可在设置中调整。迁移或备份工具时保留整个数据目录；仅重新扫描无法恢复自定义来源、锁定和下载资产绑定。`config.json` 和浏览器会话可能含凭据，请勿上传或分享。

## 常见问题

**Wiki 刷新失败或出现 Cloudflare 验证**

程序尝试直接请求，安装 `curl_cffi` 后可使用浏览器 TLS 指纹通道；仍受验证拦截时会打开专用 Edge/Chrome 会话，需要 `websocket-client`。在窗口中完成验证并保持窗口打开，工具从同一会话读取 Wiki 原文，不读取现有浏览器的 Cookie 数据库。专用配置目录被占用导致启动失败时会用临时独立会话重试一次，可能需要重新验证。

网络失败、验证失败或解析不到条目时会报错并保留旧目录，旧缓存仅供离线浏览。GUI 成功刷新 MOD Wiki 后会在后台查询 GitHub 来源的发布时间，按缓存策略回填列表；查询失败写入操作日志。设置页也保留手动导入 Cookie 与配套 User-Agent 的高级入口。

**GitHub 限流或检查速度慢**

检查使用可配置的新鲜度缓存与 ETag 条件请求，默认缓存时长为 6 小时。可在设置中填写具有目标公开仓库读取权限的 Token，查看操作日志确认失败原因。

**文件未识别、版本未知或安装后仍需人工处理**

先核对文件名和来源绑定；MOD 可关联已有条目或注册自定义来源，包可登记自定义条目。无版本文件、不可比较标签、多资产歧义和无自动下载渠道都需要人工处理，工具不会据此宣称“已最新”。

**更新时文件被占用**

关闭游戏或服务端后重试。工具会报告写入失败，已下载文件保留在缓存中；需要回退时使用「备份与恢复」。

## 开发与验证

核心代码位于 `gtnhmod/`，`cli.py` 与 `gui.py` 共用业务逻辑；`ui.py` 定义可测试的交互协议。测试与 Wiki 样例在 `tests/`。

在 Windows 仓库根目录运行现有测试：

```powershell
py -3.10 -m unittest discover -s tests
```

测试包含解析、模拟上游响应、本地 HTTP、临时目录文件操作和 Tkinter GUI 回归；GUI 测试需要可用的桌面环境。测试通过不代表真实 Wiki、GitHub 在线服务或游戏内加载已验收。

本地打包脚本默认使用 **Python 3.10**：

```powershell
py -3.10 -m pip install pyinstaller curl_cffi websocket-client Pillow
.\scripts\build_exe.bat
```

输出为 `dist/GTNHModManager.exe` 和 `dist/gtnh-cli.exe`。成品 Wiki 验证入口为 `scripts/verify_packaged_wiki.py`，资源包与光影使用 `scripts/verify_packaged_packs.py`。版本号需同时更新 `pyproject.toml` 与 `gtnhmod/__init__.py`。

推送 `v*` tag 会触发 [Release 工作流](.github/workflows/release.yml)：运行测试、构建、成品 Wiki 验证、打包并发布。普通分支推送不创建 Release；[Secret scan 工作流](.github/workflows/secret-scan.yml)检查提交历史中的凭据。贡献前请阅读 [AGENTS.md](AGENTS.md)，保持本地数据、会话、成品和恢复记录不入库。
